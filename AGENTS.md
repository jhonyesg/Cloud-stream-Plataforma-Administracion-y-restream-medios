# Cloudstream — Agent Instructions

## Database Safety Protocol (MANDATORY)

Before ANY migration, schema change, or operation that could modify or delete data:

1. **ALWAYS run `php artisan db:backup` first.** This creates a full PostgreSQL dump in `storage/app/backups/`.
2. **`migrate:fresh` IS allowed** (not blocked) but auto-restores production data from the release snapshot at `database/snapshots/release/production.json.gz`. If that file is missing, tables stay empty (run `db:export-production-data` first).
3. **NEVER run `php artisan migrate:rollback`** without checking what migrations will be reversed and whether data loss will occur. Destructive migrations now auto-restore from their per-migration snapshot (see Migration Data Safety below), but the safety net is only as good as the last `db:backup`.
4. **Use `php artisan migrate:safe`** instead of plain `migrate` for a belt-and-suspenders run: backup + migrate + verify.
5. **If a migration fails**, do NOT run `migrate:fresh` to "start over". Fix the migration and re-run `migrate`.
6. **Before dropping tables or columns**, verify the data they contain with tinker. Consider whether the data needs to be migrated first.
7. **The `pg_dump` binary for PostgreSQL 16 is at `/www/server/pgsql/bin/pg_dump`** (not the system default which is PG 14).

## Migration Data Safety

Every destructive migration (one that drops tables, columns, or truncates) **MUST** use the `WithDataSafetySnapshot` trait and declare `$criticalTables`. The trait:

- Captures a gzipped JSON snapshot of each critical table at `database/snapshots/<migration-name>/` **before** any destructive DDL runs.
- Restores those rows in `down()` so `migrate:rollback` is safe.
- Refuses to be silently bypassed by CI: `php artisan check:destructive-migrations` exits non-zero for undeclared destructive migrations.

A "release snapshot" of the full production state is kept at `database/snapshots/release/production.json.gz`. It is regenerated by `php artisan db:export-production-data` and consumed automatically by `ProductionDataSeeder` after `migrate:fresh --seed`.

### Commands

- `php artisan migrate:safe` — backup + migrate + verify (recommended over plain `migrate`).
- `php artisan db:export-production-data` — regenerate the release snapshot from the live DB.
- `php artisan db:list-snapshots` — show all per-migration snapshots on disk.
- `php artisan db:restore-snapshot <name>` — manually restore from a named snapshot (with confirmation prompt; `--force` to skip).
- `php artisan check:destructive-migrations` — CI lint; exits non-zero if any migration has destructive `up()` without the trait.

Snapshots in `database/snapshots/` are **gitignored** — never commit them. They are defense-in-depth alongside `db:backup`.

## Common Commands

- **Backup:** `php artisan db:backup`
- **Safe migrate:** `php artisan migrate:safe` (backup + migrate + verify)
- **Export production data:** `php artisan db:export-production-data`
- **List snapshots:** `php artisan db:list-snapshots`
- **Restore a snapshot:** `php artisan db:restore-snapshot <migration-name>`
- **Scan media:** `php artisan media:scan` (all channels) or `--channel=slug` (one channel). The scan rejects non-media extensions (`.py`, `.log`, `.lock`, `.tmp`, `*.upload.tmp`) and skips soft-deleted channels.
- **Media hygiene:** `php artisan media:hygiene` — detect and report `media_items` whose file is missing on disk, misclassified non-media files, and unindexed files in `channel.root_path`. **Dry-run by default.** Flags:
  - `--apply` — reclassify (no DELETEs); only safe after a recent `db:backup`.
  - `--channel=<slug-or-uuid>` — limit to one channel.
  - `--json` — emit structured JSON for piping to `jq`.
  - `--rollback-since=<ISO8601>` — restore items modified by `media.hygiene.reclassify` after the given timestamp (uses `audit_logs` snapshot).
  - All mutations are wrapped in a `DB::transaction` and produce one `audit_logs` entry per row with full `before`/`after` JSON.
- **Clear cache:** `php artisan view:clear && php artisan config:clear && php artisan route:clear`
- **Verify views:** `php artisan view:cache` (then `view:clear`)

## Emission Module — Status: DISMOUNTED (2026-07-20)

The entire emission/playout engine was **removed** on 2026-07-20 to
restructure it from scratch. What existed before (GStreamer daemon
`scripts/playout_gst.py`, `EmisionSupervisor`, `EmisionOrchestrator`,
`EmisionControlService`, `config/emision.php`, the `emision:start|stop|supervise`
commands, the `/emision` web routes/views, the systemd supervisor unit) is
**gone**. Do not look for it; it will be rebuilt clean.

### What was KEPT (scaffolding for the re-implementation)

- **`emission_state` table + `App\Models\EmissionState`** — the row of
  state fields per channel (`status`, `current_timeline_item_id`,
  `broadcast_clock_sec`, `content_position_sec`, `mode`, `pipeline_pid`,
  `overflow_sec`, `timeline_version`, etc.) and its migrations. No engine
  writes to it right now; it is the data shape the new engine will populate.
- **`App\Models\VirtualScreen`** + `/api/virtual-screens/{channelId}`
  (show/update/test-preview) + `<x-virtual-screen-editor-modal>` — the output
  configuration of a channel (resolution, codecs, bitrate, output_url, logo,
  fallback). Edited from the **Channels** view (button "Pantalla"), not from a
  dedicated emission module.
- **`program_timeline_items` + `App\Models\ProgramTimelineItem`** — the
  per-(template, day) 00:00-24:00 timeline. Built/mutated by the scheduler
  services below.
- **Timeline services** `App\Services\TimelineBuilder`,
  `TimelineMutator`, `ScheduledPlaylistResolver`,
  `ScheduledPositionCalculator`, `PlaylistDurationService`,
  `EmisionStartExceptionFactory` — used by the scheduler/Timeline API.
- **The "lock"** — the status-based start guard
  (`emission_state.status ∈ {starting, live}` ⇒ refuse double start) lives in
  the `EmissionState` model/contracts; no `Cache::lock` mutex exists.

### Timeline API (active, scheduler-owned)

`/api/schedule-templates/{template}/days/{day}/timeline`:
- `GET` — list items, overflow_sec, broadcast_clock_ref, timeline_policy.
- `POST /insert-cue` — body `{ media_item_id, at_sec }`. Validates
  `media_item.kind=ad` and `status=ready`. Splits content if `at_sec` lands
  inside it. Refuses the past.
- `DELETE /{timelineItemId}` — refuses past items. Recalculates shift of
  subsequent items.
- `POST /rebuild` — body `{ confirm: true }`. Requires explicit confirmation.

Note: the timeline `notifyControlPlane` hook pokes the live playout daemon
(`POST /reload-timeline` on the daemon's registered port) after a cue is
inserted. The daemon re-fetches the timeline, resolves the item for the current
`broadcast_clock_sec`, and restarts playback at the correct `cue_in_sec` offset.

### Cue insertion procedure (operational)

1. `php artisan db:backup` before touching a live channel's playlist.
2. Insert a future cue via the scheduler UI or
   `POST /api/schedule-templates/{template}/days/{day}/timeline/insert-cue`
   with `{ media_item_id, at_sec }` (at_sec must be in the future).
3. The playlist is persisted as `contenido anterior -> cuña -> contenido
   posterior`; the tail keeps the same `media_item_id` and `cue_in_sec` set to
   the cut point. `TimelineBuilder` materializes the same order into
   `program_timeline_items` with consecutive, non-overlapping intervals.
4. The daemon reloads the timeline, keeps the current item frozen, and applies
   the new sequence from the next safe boundary. A reload with the clock
   already inside the tail resumes the file at `cue_in_sec + offset`.
5. To roll back: delete the cue and tail `playlist_items`, clear the parent's
   `cue_out_sec`, run `Playlist::normalizeSequentialStarts` +
   `Playlist::recalculateDuration`, and rebuild the day's timeline.
6. `Playlist::normalizeSplitOrdering` repairs legacy splits whose tail was
   stored before the cue; it is also invoked on `cleanup-splits` and at
   emission start.

### Commands (active)

- `php artisan timeline:backfill [--template=ID] [--day=1,2,3] [--force]` —
  rebuild `program_timeline_items` for active templates. Default scope: all
  active templates × every block. Use `--force` to rebuild days that already
  have rows.

## Architecture Notes

- `MediaItem` references `channel_id` directly. No `MediaProvider` or
  `MediaFolder` intermediate tables.
- File path resolution: `MediaItem->channel->root_path . "/" . MediaItem->filename`
- Streaming and thumbnail endpoints are web routes (session auth), not API
  routes (sanctum auth).
- Login accepts username OR email via `login` field.
- **Timeline:** `program_timeline_items` stores a per-(template, day)
  00:00-24:00 timeline. `TimelineBuilder::buildForDay` upserts by natural key
  `(template_id, day_of_month, playlist_item_id)` so row UUIDs stay stable
  across rebuilds (this keeps `emission_state.current_timeline_item_id` FK
  valid). No supervisor advances the playhead right now — that is the job of
  the emission engine to be (re)built.
- **Emission state:** `emission_state` carries fields for both a legacy
  per-item model (`current_item_id`, `ffmpeg_pid`) and the newer playhead
  model (`current_timeline_item_id`, `pipeline_pid`, `mode`,
  `content_position_sec`, `interrupt_position_sec`, `broadcast_clock_sec`,
  `timeline_version`, `overflow_sec`). `pipeline_pid` mirrors `ffmpeg_pid`
  for compatibility. The table is present but idle until the engine is
  rebuilt.

## Restream Module

Configuration surface for re-broadcasting a channel to external platforms
(Facebook Live, TikTok Live, YouTube Live, custom RTMP). The actual playout
engine is **not** wired up — this ships the data + UI + APIs only; a future
change will consume `restream_targets` to drive the engine.

- **Tables**: `restream_quotas` (1 row per user — the habilitation) and
  `restream_targets` (N rows per user — the destination configurations).
  `restream_quotas` has `CHECK (max_outputs IN (1, 2, 3, 4))`.
- **Habilitation tiers** (admin-only, controlled from the admin panel):
  - Tier 1 (base, free) — 1 simultaneous destination.
  - Tier 2 (+1 destino, paid) — 2 destinations.
  - Tier 3 (+2 destinos, paid) — 3 destinations.
  - Tier 4 (+3 destinos, paid) — 4 destinations.
  Payment, billing and the commercial cycle are **out of scope** of this
  module. The admin simply grants/lowers the tier from the panel.
- **Client restrictions**: targets are scoped to `effectiveChannelIds()` and
  gated by the `restream.enabled` middleware alias. The active-target cap is
  enforced atomically inside `DB::transaction` +
  `RestreamQuota::lockForUpdate()` via `App\Services\Restream\RestreamQuotaGuard`.
- **`stream_key`** is encrypted via Laravel `Crypt`; never returned by list
  endpoints. `RestreamTarget::toArray()` redacts it and emits
  `stream_key_set` + `stream_key_last4` instead.
- **Admin route**: `GET /admin/restream-targets` (read-only diagnostic).
  Admin does **not** edit or delete targets (design D8).
- **Dual-implementation**: habilitation lives in admin; target CRUD lives
  in client. Both sides have a `Restream` UI surface; the modal pattern is
  `<x-restream-modal />` (admin) and `<x-restream-target-modal />` (client).

## Restream Engine

The actual playout loop for the Restream module. Each enabled target is
backed by one Python daemon (`restream_daemon/`) that follows the same
standard as the emission daemon (`emisor_python/`): supervisor loop with
restart/backoff, heartbeat every 5s, `[STATS]` every 5s, watchdog, rotated
log, and a systemd unit per target. The old PHP launcher/supervisor
(`RestreamLauncher`, `RestreamSupervisor`, `restream:supervise`) was
**removed** — the daemon self-supervises.

- **Per-target FFmpeg command** (built by `restream_daemon/daemon/target_daemon.py`
  from the config JSON written by `App\Services\Restream\RestreamOrchestrator`):
  ```
  ffmpeg -hide_banner -loglevel info -re -i {source_url}
         -c:v copy -c:a aac -ar 44100 -ac 2 -b:a 128k
         -f flv -rtmp_live live {destination_url}/{stream_key}
  ```
  Note the corrected `-rtmp_live live` flag (ffmpeg 4.4 rejects `live=1`).
  Source = `restream_targets.source_url` (NULL → fallback to
  `channel.public_hls_url`). Video is copied; audio is transcoded to AAC
  because most social destinations reject non-AAC audio. The stream key is
  decrypted by the orchestrator, written to the config JSON (0600), read
  once by the daemon, and the config file is deleted immediately; the key
  is never logged.
- **Orchestrator** (`App\Services\Restream\RestreamOrchestrator`):
  `start()` writes the config, sets `status='starting'`, spawns the daemon
  via `proc_open`, health-checks at 500ms (422 with the real cause from the
  log if it dies), and stores the daemon PID in `pipeline_pid`. `stop()`
  SIGTERMs the daemon, waits up to 10s for its `offline` heartbeat, then
  force-kills if needed.
- **Daemon self-supervision** (`restream_daemon/main.py`): if the ffmpeg
  child dies, it restarts with exponential backoff (max 5 in 60s, then 30s
  cooldown and heartbeat `error`). A watchdog restarts the child if it is
  alive but produces no progress for 15s. Each target is fully isolated:
  its own daemon, its own ffmpeg child, its own log — the N enabled slots
  never interfere with each other.
- **Heartbeat**: the daemon POSTs to
  `POST /api/internal/restream/{target}/heartbeat` (localhost-only) every
  5s with `status` (`starting`/`live`/`error`/`offline`), the ffmpeg child
  PID, and `error_message`. Laravel updates `restream_targets.status`,
  `pipeline_pid`, `last_heartbeat_at`, `last_error`. Liveness = heartbeat
  freshness (< 15s); a stale `live` target is reported as `error`.
- **Diagnostics**: `restream:status [--user=ID]` prints a table using
  heartbeat freshness. Per-target logs live in
  `storage/logs/restream/{target_id}.log` (rotated, gitignored) and are
  exposed to the UI via `GET /client|admin/restream/channels/{c}/restream-targets/{t}/log`.
- **HTTP endpoints** (client, scoped via `canAccessChannel`):
  `POST /client/channels/{c}/restream-targets/{t}/start` and `.../stop`.
  Both write `audit_logs` with `action='start|stop.restream_target'`.
- **Client/admin panels** poll the index every 10s (pausing on
  `visibilitychange`) and offer a per-target "Log de restream" accordion
  that polls every 5s while open (same pattern as the scheduler's emission
  log). Live targets show a pulsing green dot; errored targets show a red
  dot with `last_error` as tooltip.
- **FFmpeg binary** resolved from `FFMPEG_BIN` env (default `ffmpeg`) by
  the orchestrator and written into the daemon config.
- **Deployment**: per-target systemd unit
  `restream_daemon/systemd/cloudstream-restream@.service`
  (`ExecStart=/usr/bin/python3 .../restream_daemon/main.py --target-id=%i`),
  same style as `cloudstream-emission@.service`. Start is either systemd
  OR the orchestrator (HTTP), not both, to avoid double daemons.
